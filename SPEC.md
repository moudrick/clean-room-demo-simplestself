# Simplest self-provisioning clean-room demo — specification

## Scope

The configured containers are GitHub organization `GH_ORG` and LaunchDarkly project key `LD_PROJECT_KEY`, set in the ignored local `.env`. They are configuration values, not secrets, and must be non-empty safe identifiers. The organization is never created, renamed, or deleted. `LD_PROJECT_KEY` identifies a non-default, fully demo-owned project: the implementation may create and delete it. It controls all flags and environments in that project, and no other LaunchDarkly project.

The only disposable GitHub repositories are `demo-orders`, `demo-storefront`, and `demo-profile` in `GH_ORG`. The generated LaunchDarkly project contains exactly the disposable flags `demo-checkout-rollout`, `demo-legacy-profile`, and `demo-retired-banner`, and exactly the environments `production`, `staging`, `test`, and `dev`, presented in that order. Any other repository or LaunchDarkly project identifier is rejected before an API request.

## Tokens

The management CLI reads exactly four secrets: `GH_RESET_TOKEN`, `GH_DEMO_TOKEN`, `LD_RESET_TOKEN`, and `LD_DEMO_TOKEN`. Each generated evaluator application reads exactly one additional secret at runtime, `LD_EVALUATION_SDK_KEY`, which is the server-side SDK key for the environment it evaluates. `GH_ORG` and `LD_PROJECT_KEY` are required non-secret configuration values. Secrets are never command arguments, URLs, Git remotes, fixtures, output, logs, or error text. GitHub requests use `Authorization: Bearer <token>`; LaunchDarkly REST requests use `Authorization: <token>`; every JSON request body declares `Content-Type: application/json`. `doctor` requires the four management secrets and both configuration values. `audit` reads only demo tokens. `recreate` and `destroy` read only reset tokens, and never substitute a reset token when a demo token is absent. The evaluator applications never read management tokens.

`CREDENTIALS.md` is the operator guide for the one-time creation and local storage of the four management tokens. The main README links to that guide instead of mixing credential creation into the repeatable `doctor`/`recreate`/`audit`/`destroy` lifecycle.

Every GitHub and LaunchDarkly REST call uses the same bounded rate-limit policy. A `429` response is retried; a GitHub `403` is also retried when its headers or message identify rate limiting. Before retrying, the implementation prefers `Retry-After`, then the provider's `X-RateLimit-Reset` (`epoch seconds` for GitHub and `epoch milliseconds` for LaunchDarkly), and otherwise uses exponential backoff beginning at sixty seconds. It waits through the indicated window and adds up to one second of jitter. A request is attempted at most six times total. If the required single wait exceeds five minutes, or all retries are exhausted, the command fails nonzero without issuing an early retry. During `recreate`, a permitted rate-limit wait updates the progress display immediately and at most every ten seconds with the provider, retry number, and rounded remaining wait; it never displays a token, request header, or URL. Rate-limit handling reuses the same method, target, body, token role, redaction, and official-origin checks.

Create the GitHub reset fine-grained PAT for resource owner `GH_ORG`, all organization repositories, Administration read/write, Contents read/write, and Metadata read (normally automatic), with short expiration. Create a separate demo PAT for the same owner and repositories with Contents read-only and Metadata read, also short-lived. The organization must allow members/tokens to create and delete organization repositories; GitHub Administration write is required for those operations.

In LaunchDarkly, use **Organization settings → Authorization → Create token**. Create personal token `featureflag-demo-reset` with Writer base role and API version `20240415`, able to list/create/delete the non-default demo project and all of its environments and flags. Create `featureflag-demo-read` with Reader base role and the same API version, able to list projects and flags. LaunchDarkly shows access-token secrets once: copy each immediately into ignored `.env`. Server-side SDK keys are not API access tokens and cannot manage resources. LaunchDarkly automatically gives each created environment a default server-side SDK key; no additional manual credential creation is required. `recreate` retrieves the four freshly generated default SDK keys and writes them only to ignored `runtime/sdk-keys.env`; it never prints them. Each evaluator process receives exactly the key for the environment it models. The three applications in one environment share that environment's key, so this is the LaunchDarkly project/environment credential boundary rather than per-application credential isolation. Docker Compose uses all four keys across its twelve services.

## Commands

`node demo.mjs doctor` is the first command to run. It is read-only: it checks presence, authentication, configured-organization access, existing disposable-repository read access for both GitHub tokens, LaunchDarkly project-list access for both LaunchDarkly tokens, and official response origins. It prints the compact capability table. It succeeds whether the demo project is present or absent. Write/delete capability is reported as verified only during `recreate`; it is never tested by mutation in doctor. Any authentication, identity/access, scope/read, origin, or identifier mismatch exits nonzero. A failed check identifies its token variable and check type, but never its token value.

`node demo.mjs recreate --confirm <LD_PROJECT_KEY value>` uses only reset tokens. It performs reset-token read checks, prints every exact target, requires the exact configured-project confirmation string, deletes only existing disposable repositories and the exact demo project, confirms each deleted repository and project is absent with at most ten one-second read-only checks, and creates three public repositories with an initial commit. It creates the project with exactly `production`, `staging`, `test`, and `dev`; Production and Staging are explicitly marked critical, while Test and Dev are explicitly non-critical. It then commits synthetic source as a child commit, preserving the deliberate source-commit timestamps, creates three boolean flags, and restores the deterministic targeting in every generated environment described below. Finally it transactionally replaces only the generated contents of local `runtime/`: it shallow-clones the three public repositories over HTTPS into `runtime/repos/` without embedding a token, then writes the ignored environment SDK keys. If any clone or key-file write fails, it removes both generated runtime artifacts rather than leaving a partial workspace. `demo-checkout-rollout` is in two files across two repositories with recent synthetic commits; `demo-legacy-profile` is in one file in one repository with deliberately fabricated old author/committer dates; `demo-retired-banner` is absent. A destructive-operation failure identifies the reset-token role, action, and exact target, but never a token value.

`recreate` is a self-contained destructive reset whether its targets are populated, partially present, or already absent; running `destroy` first is unnecessary. A repeat run deletes all history in the three repositories and all flags, environments, SDK keys, targeting, and accumulated evaluations in the configured demo project, then rebuilds them and replaces local `runtime/repos/` and `runtime/sdk-keys.env`. Before repeating it, the operator must stop Compose so no process continues with invalidated SDK keys. It never deletes or changes the GitHub organization, LaunchDarkly account, another repository or project, the tracked Compose files, or locally built Docker images. Its line-oriented fifteen-step progress bar identifies the current major phase. A rate-limit countdown temporarily annotates the same completed-step count.

`node demo.mjs audit` uses only demo tokens. It lists configured-project flags, code-searches the configured organization, accepts only the three repositories, verifies each result on its current default branch, and prints `FLAG | VERIFIED FILES | REPOSITORIES | LAST FILE COMMIT | RESULT`. The former vague `run` command is removed rather than retained as a compatibility alias because the project has not made its first public release.

`node demo.mjs destroy --confirm <LD_PROJECT_KEY value>` uses only reset tokens, requires exact confirmation, and deletes the three disposable repositories and the exact demo project. Deleting the project removes all its flags and environments, returning it to the state before this demo was created. After successful remote deletion it removes only generated `runtime/sdk-keys.env` and `runtime/repos/`; the tracked Compose definition and runtime documentation remain. Missing targets are reported as already absent. It cannot delete the account's last project, so `LD_PROJECT_KEY` must not be the default or last project. A destructive-operation failure identifies the reset-token role, action, and exact target, but never a token value.

## Generated repositories and evaluation

Each generated repository contains an independently runnable Node.js server-side LaunchDarkly evaluator, a Node.js 24 Alpine Dockerfile, its minimal package manifest, and synthetic source only. The image disables npm's update notifier so routine Compose builds and runs do not print upgrade advertising; it retains the npm version supplied by the pinned Node base-image line rather than installing an unpinned latest version. One-shot mode accepts `--context-key`, `--plan`, `--region`, `--cohort`, `--instance`, and `--evaluations`. The first five values form synthetic `user` contexts: `key` is derived from `--context-key`; `plan`, `region`, `cohort`, and `instance` are custom attributes. Identifier values must be safe and non-empty. `--evaluations` is an integer from 1 through 1000 and defaults to 10. A count of one uses the exact context key; a larger count appends a zero-padded sequence to create distinct context keys with the same supplied targeting attributes. The other defaults are `demo-user`, `free`, `eu`, `control`, and `LOCAL1`. Thus one one-shot invocation emits ten useful evaluations per owned flag by default. The evaluator reads only `LD_EVALUATION_SDK_KEY`, waits for SDK initialization, evaluates its owned flag or flags, explicitly flushes analytics events, closes the SDK, and exits. It never prints the SDK key or a management token.

Long-running mode is `npm run traffic -- --profile <production|staging|test|dev> [--interval-seconds <10..86400>]`. It keeps one SDK client open, emits its first batch immediately, defaults to a five-minute interval, emits deterministic synthetic context mixtures that exercise both targeting and fallthrough rules, and varies evaluation volume between weekday UTC 07:00–19:00 business hours and quiet periods. Per evaluator and cycle, Production emits 100 business-hour or 40 quiet evaluations, Staging emits 30 or 12, Test emits 10 or 4, and Dev emits 2 or 1. This provides the fixed volume order Production much greater than Staging, Staging greater than Test, and Test greater than Dev, including clearly non-single-digit initial activity outside Dev.

Traffic contexts include the non-secret repository name as `service` and a synthetic deployment `instance`. Production deterministically weights `WestEU1`, `EMEA4`, and `SouthAM2`; Staging weights `STG1` and `STG2`; Test uses `TEST1` and `TEST2`; Dev uses `DEV1`. These are context values inside the four fixed LaunchDarkly environments, not additional environments. Production and Staging instance weights deliberately produce different evaluation counts. The four profiles also produce distinct but repeatable true/false distributions. Configurable traffic definitions are postponed. On `SIGINT` or `SIGTERM`, the process wakes promptly, flushes pending analytics events, closes the SDK, and exits. Restarting traffic adds evaluations to the existing flags; it never resets or backdates data.

`demo-orders` and `demo-storefront` each evaluate `demo-checkout-rollout`; `demo-profile` evaluates `demo-legacy-profile`. Compose runs those applications in all four environments, so both active flags receive evaluation activity in Production, Staging, Test, and Dev. No generated application evaluates `demo-retired-banner` in any environment; that complete absence is deliberate evidence for its dead-candidate scenario and is the sole exception to evaluation coverage. Each evaluator prints only its repository name, flag key, evaluated boolean value, and non-secret context attributes.

In every generated environment, `recreate` configures the disposable flags as follows:

- `demo-checkout-rollout` is on for `cohort=checkout-beta` or `plan=enterprise`; it is off for the fallthrough rule.
- `demo-legacy-profile` is on for `region=legacy`; it is off for the fallthrough rule.
- `demo-retired-banner` is off and has no evaluator.

This permits repeatable demonstrations of distinct targeting rules, for example `--cohort checkout-beta`, `--plan enterprise`, or `--region legacy`, while all other default contexts receive the off variation.

## Runtime traffic workspace

Tracked `runtime/compose.yaml` defines twelve long-running services: the three generated repositories in each of the four environments. It builds only from the shallow clones in `runtime/repos/`, uses `restart: unless-stopped`, rotates local container logs, and passes each process exactly one environment-specific SDK key from ignored `runtime/sdk-keys.env`. It never mounts the management `.env` or exposes a port. The generated traffic workspace is local-only and must not be committed.

Before `recreate` or `destroy`, the operator must stop Compose so old containers do not continue using invalidated SDK keys. After `recreate`, one Compose `up --detach --build` starts all traffic. The README provides copy-pasteable `ps --all` and recent `logs` commands for checking all twelve services. Compose may be stopped and restarted without losing LaunchDarkly history; evaluations remain cumulative until the project is deleted by `recreate` or `destroy`. The host or Docker engine must remain running for traffic to continue over days or weeks.

LaunchDarkly flag-evaluation history is populated only by live SDK variation calls. The demo does not attempt backfill: metric-event import accepts custom metric events rather than historical flag evaluations, and REST evaluation calls do not populate flag status or insights.

## Verification and continuous integration

Local verification after a change is `node --check demo.mjs`, `node --check lib.mjs`, and `npm test`. Tracked `.github/workflows/test.yml` uses the current `actions/checkout@v7` and `actions/setup-node@v7` releases and runs the same checks with Node.js 24 on every push to `main`, matching the initial direct-to-main development model without deprecated Node.js 20 action runtimes. The workflow has read-only repository-content permission, receives no secrets, and never runs `doctor`, `recreate`, `audit`, `destroy`, Docker traffic, or an external API request. Pull-request gating is outside the current scope.

## Audit semantics and errors

`REFERENCED` requires one or more verified current-default-branch files. `STALE CANDIDATE` requires verified files and an old newest matching-file commit. `DEAD CANDIDATE` requires complete, successful evidence of no matches. Any failed, unauthorized, rate-limited, malformed, capped, or incomplete evidence yields `UNKNOWN`, never a candidate. Candidates only begin investigation and never authorize deletion. “Last file commit” is the newest default-branch commit touching a currently matching file, not a flag evaluation. API errors include their HTTP status and, when present, a short redacted server message; they never include request headers or token values.

## Acceptance and non-goals

Acceptance is fixed-scope enforcement, command-specific token isolation, exact destructive confirmation, deterministic synthetic evidence, redacted errors, and mocked tests proving incomplete evidence cannot be stale/dead. Generated evaluator applications must support batched one-shot and long-running operation, emit and flush evaluations for their owned flags in all four environments, demonstrate targeting and fallthrough using only synthetic contexts, shut down cleanly, and never evaluate `demo-retired-banner`. Mocked verification must cover the fifteen-step recreate sequence and rate-limit countdown, removal of the `run` command, runtime key-file generation, exact token-free clone targets, fixed Compose service and environment ordering, deterministic instance weights and traffic-volume ordering, and bounded rate-limit behavior. Pushes to `main` must run the local syntax checks and mocked tests without secrets or external service access. This experimental reference deliberately does not provide production hardening, configurable traffic-pattern definitions, historical evaluation backfill, general repository discovery, presentation assets, recordings, publication workflows, pull-request gating, or management of accounts or organizations.
